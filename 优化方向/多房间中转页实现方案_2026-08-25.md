# 多房间 + 中转页实现方案分析（2026-08-25）

> 需求：点击进入跑团平台 → 跳转**中转页** → 中转页内**创建房间 / 加入房间** →
> 加入房间需输入**密码（房主设置）** → 进入对应房间实例。
> 本文档为分析与设计，未实施。

---

## 一、现状架构（改造基线）

| 全局状态 | 位置 | 现状 |
|---|---|---|
| DM 身份 | `web/app.py:368` `_dm_name/_dm_ip/_dm_user_id` | **全局唯一**，首个加入者为 DM |
| 在线用户 | `_online_users` 全局 dict | 全平台一个房间 |
| 战斗状态 | `_combat_state/_combat_state_ts`（PG combat_state 表 id=1 单行） | 全局一份 |
| 共享画布 | `web/shared_state.py`（PG SharedCanvas 单行表） | 全局一份 |
| 聊天消息 | `chat_messages` 表 | **无房间字段** |
| WS 协议 | `/ws`（Flask-Sock） | 消息无 room_id 维度 |
| 房间 API | `/api/room/join|heartbeat|leave|users`（app.py 3719-4360） | 单房间实现 |

**核心架构限制**：`_dm_name` 全局唯一 → 多桌无法并存（分析文档第七章第 7 项 ⭐⭐⭐⭐⭐）。

## 二、目标流程

```
官网/导航「跑团平台」入口
   │  ┌─────────────────────────┐
   └▶│ 中转页 /rooms（房间列表） │

```

## 三、实施设计

### 3.1 数据层（新表 rooms）

```sql
CREATE TABLE rooms (
  id            SERIAL PRIMARY KEY,
  name          VARCHAR(64) NOT NULL UNIQUE,   -- 房间名（唯一，防重名）
  password_hash VARCHAR(256) DEFAULT '',        -- 房主设置密码（哈希，空=无密码）
  owner_user_id INTEGER,                        -- 房主用户 id（可空：未登录游客房主）
  status        VARCHAR(16) DEFAULT 'open',     -- open/closed（房主可关房）
  created_at    TIMESTAMP DEFAULT now()
);
```
- 密码用 `werkzeug.security.generate_password_hash`（与 users 表同套）
- 房主可改密/清密/关房（新 API）；修改密码后旧成员不受影响（仅限制新加入）

### 3.2 后端改造（web/app.py + shared_state.py）

**a) 房间注册表（内存）**
```python
ROOMS: dict[int, dict] = {
  room_id: {
    'dm_name': ..., 'dm_ip': ..., 'dm_user_id': ...,
    'online_users': {...},        # 原 _online_users 移入
    'combat_state': ...,          # 原 _combat_state 移入
    'created': ...,
  }
}
# 默认房间 room_id=0（main）：老客户端/未指定房间时进默认房间，数据零迁移
```

**b) 状态隔离清单**
| 状态 | 改造 |
|---|---|
| `_dm_name` 系 | 移入 `ROOMS[room_id]`，DM 晋升逻辑按房间独立 |
| `_online_users` | 移入房间；心跳/清理/加入/退出全带 room_id |
| `_combat_state` | 移入房间；`combat_state` 表加 `room_id` 列（幂等补列，老行 room_id=0） |
| `shared_state` | SharedCanvas 表加 `room_id` 列，读写按房间过滤（老行 0） |
| `chat_messages` | 表加 `room_id` 列；send/messages 按房间过滤（老行 0） |
| WS 消息 | join/heartbeat/init/sync/canvas_update/combat_update 等统一带 room_id 字段 |

**c) 新 API**
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/rooms` | 创建房间（name + password，返回 room_id；创建者成为房主+DM） |
| GET | `/api/rooms` | 房间列表（名称/房主名/在线人数/状态，**不含密码**） |
| POST | `/api/rooms/join` | 加入验证（room_id + password → ok/密码错误 403） |
| POST | `/api/rooms/<id>/password` | 房主改密/清密/关房（鉴权：仅房主） |
| POST | `/api/rooms/<id>/leave` | 退出房间（房主退出 → 剩余最早加入者晋升 DM） |

**d) 兼容策略**：所有房间 API 的请求/响应加 `room_id` 字段，**默认 0（主房间）**；
前端不传 room_id 时全部行为与现在完全一致 → 改造可分批上线、老页面不受影响。

### 3.3 中转页（新模板 + 前端）

- `web/templates/rooms.html` + `web/static/rooms.js`（冰霜主题与 portal 一致）
  - 房间列表：卡片式（房名/房主👑/在线人数🟢/状态），点击「加入」→ 弹窗输密码（无密码直接进）
  - 创建表单：房间名 + 密码（可留空）+ 「创建并进入」
  - 成功后：`location.href = '/map?room=' + room_id`（sessionStorage 存 room_id + 身份）
- 导航改造：各页面「进入跑团平台」入口 → 跳 `/rooms` 中转页（门户首页/导航栏多处入口同步）

### 3.4 前端页面改造（map/chat/dice3d/combat/events）

- 统一从 URL 参数 `?room=`（或 sessionStorage `dnd_room_id`）取 room_id
- 所有轮询/WS/广播请求带 room_id（`/api/chat/messages?room=`, `/api/shared-canvas?room=`…）
- 加入覆盖层（map-page.js doJoin）：显示当前房间名，身份选择不变
- 好友私聊/北境存档等**跨房间**功能不受影响（按用户维度）

### 3.5 密码机制细节

- 创建时房主设置密码 → 哈希入库；加入时后端 `check_password_hash` 校验，错误返回 403「房间密码错误」
- 所有房间都需要密码
- 密码只拦**加入**，不拦已在房间内成员（心跳无需密码）
- 房主本人重进：若房间已存在，用密码或房主身份（登录态 user_id 匹配）进入

## 四、实施分期（建议顺序）

| 期 | 内容 | 范围 | 预估 |
|---|---|---|---|
| 一期 | rooms 表 + rooms API + 中转页 /rooms + 房间注册表（DM/在线/聊天按房间隔离）+ 前端入口改造 | app.py 房间区 + 新模板 | 核心骨架 |
| 二期 | 画布（shared_state）+ 战斗（combat_state）按房间隔离 + WS 协议带 room_id | shared_state.py + map.js/combat.js | 数据隔离补齐 |
| 三期 | 房主管理增强（改密/踢人/关房）、房间列表页刷新/搜索、DM 移交 | app.py + rooms.js | 打磨 |

## 五、风险与注意点

1. **WS 协议是最大改造点**：`/ws` 的 init/sync/op 消息全链路要带 room_id，服务端按连接绑定房间（`ws_room_map: {ws: room_id}`），前端每页连接前先确认房间
2. **默认房间零迁移**：room_id=0 兜底保证老数据（画布/聊天/战斗）无缝可用——这是分期改造的关键前提
3. **DM 晋升竞态**：多房间下 DM 晋升/离开逻辑需按房间加锁（threading.Lock 每房间一把）
4. **缓存版本号**：改 map.js 等需同步 bump map.html（当前 v83）
5. **后端无热重载**：分期上线需重启服务；建议一期完成后再动前端
6. 身份伪造（sessionStorage 可改 role）是既有问题（分析文档 3.2 第 2 项），多房间后建议一并做服务端签发
