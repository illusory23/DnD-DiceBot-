================================================================================
  多人实时 3D 掷骰桌面 — 完整方案分析
================================================================================
  日期：2026-07-22
  目标：多人共享 3D 掷骰动画，一人投掷全员可观看

================================================================================
  一、需求拆解
================================================================================

  核心场景：
    玩家A 在地图页点击掷骰 → 3D 动画播放
    玩家B/C/D 同时看到同样的 3D 动画
    每个玩家的骰子独立，但动画共享

  技术难点：
    1. dice-box 使用 ammo.js WASM 物理引擎，随机种子不可控
    2. 相同参数在不同客户端产生不同动画结果
    3. 浏览器渲染的 canvas 无法直接"转发"给其他客户端
    4. 多人同时投掷时画面叠加问题


================================================================================
  二、五种方案逐一分析
================================================================================


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  方案 A：权威结果覆盖（推荐当前实施）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原理：
    投掷者本地 dice-box 动画 → 广播结果
    其他人不播动画，直接显示结果数字

  技术栈：     Flask WebSocket + sessionStorage
  新增代码量： ~80 行
  开发周期：   1-2 小时

  优势：
    ✅ 实现简单，无架构改动
    ✅ 结果精度 100%（广播实际值）
    ✅ 聊天室已有广播机制，直接复用
    ✅ 无额外性能开销
    ✅ 可立即上线

  劣势：
    ⚠️ 只有投掷者看到 3D 动画
    ⚠️ 其他人仅看到文字结果
    ⚠️ 缺少"临场感"

  优化方向：
    1. 结果通知动画化
       → 收到广播后在屏幕中央弹出骰子面飞入动画（CSS，非 3D）
       → 每个骰子面显示对应数值，持续 2 秒后缩入侧边栏
    2. 音效反馈
       → 投掷音 + 骰子落定音（短音频，<100KB）
    3. 排行榜/统计面板
       → 记录每人掷骰次数、最高值、最低值、暴击次数

  评分：
    实现难度   ★☆☆☆☆ (1/5)
    同步质量   ★★☆☆☆ (2/5)
    用户体验   ★★★☆☆ (3/5)
    性能开销   ★★★★★ (零开销)
    维护成本   ★★★★★ (极低)

  ══════════════════════════════════════════
  推荐度：⭐⭐⭐⭐⭐ (当前最优)
  ══════════════════════════════════════════


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  方案 B：本地独立重放 + 文字覆盖
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原理：
    广播参数 + 结果
    每个客户端收到后本地调用 diceBox.roll() 重放动画
    动画结果被忽略，覆盖显示权威结果

  技术栈：     Flask WebSocket + dice-box 本地实例
  新增代码量： ~200 行
  开发周期：   5-8 小时

  优势：
    ✅ 每个观看者都能看到 3D 动画
    ✅ 结果仍然是权威的（文字覆盖）
    ✅ 不依赖投掷者持续在线

  劣势：
    ⚠️ 动画与结果数字不匹配（骰子面显示 3 但覆盖写"5"）
    ⚠️ 需要每个客户端加载完整 dice-box（1.5MB WASM）
    ⚠️ 多人同时观看时各自独立加载，资源浪费
    ⚠️ 移动端性能差（WASM 内存 30MB+）

  优化方向：
    1. 延迟显示权威结果
       → 本地动画播完后 0.5s 再弹出权威数字
       → 减少"结果不匹配"的突兀感
    2. 提前预热
       → 检测到有投掷事件时预加载 dice-box 模块
       → 点击观看按钮时立即展示，无需等待加载
    3. 降级策略
       → 检测设备性能（内存 < 4GB 或移动端）→ 自动降级为方案 A

  评分：
    实现难度   ★★★☆☆ (3/5)
    同步质量   ★★★☆☆ (3/5)
    用户体验   ★★★★☆ (4/5)
    性能开销   ★★☆☆☆ (高开销)
    维护成本   ★★★☆☆ (中)

  ══════════════════════════════════════════
  推荐度：⭐⭐⭐ (体验好但成本高)
  ══════════════════════════════════════════


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  方案 C：WebRTC Canvas 推流
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原理：
    投掷者浏览器用 captureStream() 捕获 dice-box canvas
    通过 WebRTC DataChannel / MediaStream P2P 传输给其他客户端
    其他客户端用 <video> 标签播放

  技术栈：     RTCPeerConnection + MediaStream + WebSocket 信令
  新增代码量： ~500 行
  开发周期：   2-4 天

  优势：
    ✅ 完全同步，画面 100% 一致
    ✅ 不需要每个客户端加载 dice-box
    ✅ 低延迟（通常 <200ms）

  劣势：
    ⚠️ 依赖投掷者浏览器持续运行且网络正常
    ⚠️ 投掷者关闭页面 → 所有人看不到
    ⚠️ WebRTC P2P 穿透需要 STUN/TURN 服务器
    ⚠️ 多人观看时投掷者上行带宽压力（每路 ~2Mbps）
    ⚠️ 最多 3-5 个观看者（浏览器 P2P 限制）
    ⚠️ canvas.captureStream 在 Firefox 支持不完整

  优化方向：
    1. SFU 中继模式
       → 搭建 mediasoup/Janus 转发服务器
       → 投掷者只需推 1 路 → 服务器分发给 N 人
       → 支持数十人同时观看
    2. 自动降级
       → 观看者超过 5 人 → 降级为方案 B
    3. 录制回放
       → 服务器录制推流 → 后续加入者可看回放
    4. 分辨率自适应
       → 根据观看者数量动态调整推流分辨率

  评分：
    实现难度   ★★★★☆ (4/5)
    同步质量   ★★★★★ (5/5)
    用户体验   ★★★★★ (5/5)
    性能开销   ★★★☆☆ (投掷者有压力)
    维护成本   ★★★★☆ (高)

  ══════════════════════════════════════════
  推荐度：⭐⭐⭐ (体验完美但基础设施重)
  ══════════════════════════════════════════


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  方案 D：服务端渲染推流
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原理：
    服务端运行 headless Chrome + dice-box
    每次掷骰 → Puppeteer 调用 → 录制 canvas → HLS/WebRTC 推流
    客户端用 <video> 播放

  技术栈：     Puppeteer + FFmpeg + Nginx-RTMP / mediasoup
  新增代码量： ~1500 行
  开发周期：   2-4 周

  优势：
    ✅ 完全同步，不依赖任何客户端
    ✅ 无限观看者（HLS 推流）
    ✅ 录制天然支持（可直接存视频文件）
    ✅ 骰子结果可由服务端控制

  劣势：
    ⚠️ 需要服务器 GPU（或 CPU 软渲染，性能极差）
    ⚠️ Puppeteer 内存开销大（每实例 ~200MB）
    ⚠️ 延迟高（HLS 通常 2-5 秒）
    ⚠️ 运维复杂（Chrome 崩溃恢复、内存泄漏管理）
    ⚠️ 成本高（云 GPU 服务器 ¥500+/月）

  优化方向：
    1. 渲染池化
       → 预启动 N 个 headless Chrome 实例
       → 掷骰请求到来时分发到空闲实例
       → 复用减少启动延迟
    2. WebGL 服务端
       → 使用 headless-gl + Node.js 直接调 Three.js
       → 避免完整 Chrome 开销
    3. 按需渲染
       → 仅当有观看者时才渲染
       → 无观看者时仅记录结果文本

  评分：
    实现难度   ★★★★★ (5/5)
    同步质量   ★★★★★ (5/5)
    用户体验   ★★★★★ (5/5)
    性能开销   ★★☆☆☆ (服务器重)
    维护成本   ★★★★★ (极高)

  ══════════════════════════════════════════
  推荐度：⭐ (商业产品级别，个人项目不推荐)
  ══════════════════════════════════════════


━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  方案 E：确定性种子引擎 + 帧同步
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  原理：
    替换 dice-box 为自定义确定性物理引擎
    每次掷骰生成一个随机种子
    所有客户端用同一种子 → 产生完全相同的动画
    通过 WebSocket 每 16ms 同步一次帧号，保证步调一致

  技术栈：     cannon.js (确定性) 或自研简化物理 + Three.js + WebSocket
  新增代码量： ~3000 行
  开发周期：   4-8 周

  优势：
    ✅ 所有客户端完全一致
    ✅ 不需推流，带宽极小（仅种子 + 参数）
    ✅ 无限观看者
    ✅ 结果由服务端种子控制，防作弊

  劣势：
    ⚠️ 需要完全重写骰子引擎
    ⚠️ cannon.js 也有浮点精度差异（跨平台）
    ⚠️ 帧同步开发极其复杂
    ⚠️ 骰子模型、纹理、物理参数全部要重建
    ⚠️ 项目周期长，风险高

  优化方向：
    1. 固定精度
       → 所有碰撞计算使用定点数而非浮点
       → 确保 Win/Mac/Linux/ARM 结果完全一致
    2. 帧缓冲
       → 提前计算 3 帧帧数据
       → 网络抖动时仍有缓冲
    3. 校验机制
       → 每 60 帧服务端下发校验值
       → 不一致的客户端自动重连重新同步

  评分：
    实现难度   ★★★★★ (5/5)
    同步质量   ★★★★★ (5/5)
    用户体验   ★★★★★ (5/5)
    性能开销   ★★★☆☆ (每个客户端独立计算)
    维护成本   ★★★★★ (极高)

  ══════════════════════════════════════════
  推荐度：⭐⭐ (理想方案但成本不可接受)
  ══════════════════════════════════════════
