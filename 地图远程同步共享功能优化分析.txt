# 地图远程同步共享功能 & 整体优化分析报告

分析对象：骰娘 Web 版（dnd_bot.py --web / web/ 目录）
分析日期：2026-07-17


================================================================
一、地图同步现状架构
================================================================

浏览器(DM/PL)                        Flask (0.0.0.0:5000, debug=True)
 ├─ WebSocket /ws ◄──实时增量广播──► flask-sock 处理器 (app.py:163-210)
 ├─ GET /api/shared-canvas?since=ts ──300ms轮询──► 全量返回(剔除dataURL)
 ├─ POST /api/shared-canvas ──100ms防抖推送──► 增量/全量合并 (app.py:243-266)
 └─ GET /api/shared-canvas/layer/<id> ──► 单图层图片(base64解码)
                                          │
                                    _shared_canvas (内存 dict, 无锁)
                                          │ 3秒防抖
                                    shared_canvas.json (当前 1.8MB)

数据分 5 类：strokes（笔迹）、layers（图层含 base64 底图）、tokens、
texts、fog（迷雾多边形）。另有一套独立的 /api/map-state 轻量推送通道
（app.py:2815-2845）和 ws_server.py 的 5001 端口独立 WS 服务器——
后者是死代码，--web 从未启动它。


================================================================
二、地图同步的核心问题与解决方案（按严重程度排序）
================================================================

----------------------------------------------------------------
【P0-1】地图底图以 base64 内嵌 JSON，全链路反复传输
----------------------------------------------------------------
现状：实测 shared_canvas.json 1.8MB 中 1.75MB 是单个图层的 dataURL。
它的传播路径：
 - 每个新 WS 连接收到的 init 消息全量包含它（app.py:168-169）
 - 前端每次 layers_update（哪怕只改可见性/微调偏移）都把整个 base64
   重新广播给所有客户端（map.js:3727-3744）
 - pushSharedCanvas 每次 HTTP 推送也带上它（map.js:4206）
 - 每 3 秒防抖落盘要序列化整个 1.8MB JSON（shared_state.py:39-58）

一张 2000×1500 的地图 base64 约 4-8MB，4 个玩家 = 每次图层操作广播
16-32MB 流量。

方案：
 1. 图片与状态分离：图层图片改为上传到 maps/ 目录（已有
    /maps/<filename> 静态服务，app.py:2373），画布状态里只存
    {"id","url":"/maps/xxx.png","offsetX",...}。前端已经有
    loadServerMap，只需让「导入本地图片」走一次
    POST /api/resources/upload 再引用 URL。
 2. layers_update 消息只传元数据（偏移/缩放/可见性），图片由浏览器
    HTTP 缓存承担。
 3. 落盘的 JSON 会从 1.8MB 缩到几 KB，3 秒防抖序列化开销也随之消失。

----------------------------------------------------------------
【P0-2】迷雾数据无条件下发给所有玩家（服务端不过滤）
----------------------------------------------------------------
现状：fog 多边形坐标通过 init 和 fog_update 完整发给 PL
（app.py:168-169, 215-240）。虽然前端对 PL 用不透明黑渲染并隐藏迷雾
下的 token（map.js:1227-1229, 1313-1333），但玩家打开 DevTools 或
直接 fetch('/api/shared-canvas') 就能拿到：
 - 迷雾多边形的精确形状（暴露"哪里有东西被藏起来"）
 - 迷雾下所有 token 的名字、位置、HP（token 隐藏只是 display:none）

方案：服务端按身份过滤。给 /ws 连接和 GET 请求附带房间身份（现有
_online_users 的 role 可用），PL 视角下：
 - 在服务端用同样的「点在多边形内」判定剔除迷雾覆盖的 tokens/texts
   （把 updateAllFogCoverage 的逻辑移植到 Python 端）
 - fog 只下发「需要遮黑的区域」，不下发 DM 备注等元数据
 - 注意前提是先解决"身份由客户端自报"的鉴权问题（见第三节）

----------------------------------------------------------------
【P0-3】无并发保护：多线程读写共享状态无任何锁
----------------------------------------------------------------
现状：_shared_canvas 被 WS 处理线程、HTTP 请求线程、threading.Timer
保存线程同时读写，全程无锁（shared_state.py:81-95）；_save_to_disk
序列化时若主线程正在 extend 列表，可能写出损坏的 JSON。同样无锁的还有
_chat_messages、_online_users、_map_state、_combat_state。

方案：加一把模块级 threading.RLock，所有 update/append/get/save 入口
加锁；_save_to_disk 在锁内做 copy.deepcopy（状态瘦身后成本很低）再在
锁外写文件。这是十几行的改动，收益极大。

----------------------------------------------------------------
【P1-1】无版本号、无冲突处理，「增量合并」还不能删除
----------------------------------------------------------------
现状：
 - 唯一的变更标识是 time.time() 浮点时间戳，仅用于「有没有变」，不用于
   冲突检测——多客户端并发写为最后写入者获胜。
 - POST 增量模式按 id 合并 layers/tokens/texts（app.py:260-264），
   但没有删除语义：客户端删掉一个 token 后发剩余列表，服务端里旧 token
   依然存在，下次全量拉取时"幽灵 token"复活。
 - 前端笔迹合并靠 state.strokes.slice(brushStrokes.length) 的长度假设
   （map.js:4230），两人同时画线立刻错乱。

方案：
 1. 服务端维护单调递增 version（int），每次变更 +1；客户端拉取带
    since_version，广播消息附带 version，客户端丢弃过期消息。
 2. 把消息改成操作语义而不是全量列表：token_add / token_move /
    token_remove / stroke_add / fog_set。服务端按操作应用到权威状态，
    天然解决删除问题和"拖动一个 token 却广播全部 tokens"的浪费
    （map.js:1124 现在拖完一个 token 就全量发 tokens_update）。
 3. 笔迹给每条 stroke 一个客户端生成的 uuid，合并按 id 去重，替代长度
    假设。

----------------------------------------------------------------
【P1-2】WS 与 HTTP 轮询双通道并存，互相打架
----------------------------------------------------------------
现状：
 - WS 正常时前端跳过 HTTP 拉取（map.js:4221），但推送不检查 WS 状态，
   每次修改除了 WS 广播还要 HTTP POST 一次（map.js:4196-4214）——双倍
   写流量，且两条路径写同一份内存可能交错。
 - WS 断开时退化为 300ms 轮询（map.js:4298），每次都返回全量状态
   （app.py:235-240 即使 changed:false 也带全量）——每分钟 200 个大
   响应。
 - WS 重连后只 flush 待发队列、不拉取服务端最新状态（map.js:3612-3616），
   离线期间他人的修改直接丢失，本地与服务端永久不一致直到手动刷新。

方案：
 1. 确立「WS 为唯一实时通道，HTTP 仅作降级」：pushSharedCanvas 开头加
    if (ws已连接) return（与拉取对称）。
 2. changed:false 时不要返回 state 本体，只返回 {changed:false}；轮询
    间隔放宽到 1-2 秒。
 3. 重连的 onopen 里主动发一个 {type:'sync_request', since_version}
    让服务端回增量（或干脆重发 init），这是修复一致性的关键一步。

----------------------------------------------------------------
【P1-3】拖拽过程中收到远程更新 → DOM 悬空引用
----------------------------------------------------------------
现状：收到 tokens_update 时无差别删光重建所有 token DOM
（map.js:3747-3752）。若用户正在拖拽，dragTarget 指向已被移除的对象，
mouseup 写入无效，token 视觉上跳变消失。

方案：
 - 收到远程更新时若 dragTarget 非空，跳过对该 token 的重建（本地拖拽
   优先），拖拽结束后再和最新远程状态对账；
 - 改为差量更新 DOM：按 id diff，只更新变化的 token 的 style.left/top，
   不重建整个 overlay——同时解决"1 个 token 移动重建全部 DOM"的性能
   问题（texts_update、layers_update 同理，map.js:3729-3759）。

----------------------------------------------------------------
【P2】其他地图同步问题
----------------------------------------------------------------
 - ws_server.py（5001 端口）整套死代码，与 flask-sock 版逻辑重复且行为
   有差异 → 直接删除，避免日后误维护两套。
 - 3 秒防抖保存：进程崩溃丢最后 3 秒；debug=True 下 Werkzeug 报错页不会
   救你（shared_state.py:9,71-78）→ 保留防抖，但补充「最长 N 秒必落盘
   一次」的兜底；退出钩子 atexit 强制保存。
 - 「空画布不保存」逻辑：用户主动清空全图后重启，旧内容复活
   （shared_state.py:52-54）→ 区分「空但已确认」与「疑似异常空」，如
   clear_all 时立即写盘。
 - strokes 超 5000 条静默截断（shared_state.py:92-93）→ 提供"合并笔迹
   为图层位图"功能（bake），既省流量又不丢画。
 - WS 广播 except Exception: pass，死连接不清理（flask-sock 版同样吞
   异常，app.py:200-207）→ 发送失败即从连接集移除，并记一条日志。
 - /api/map-state 与 shared-canvas 双轨并行，语义重叠
   （app.py:2815-2845）→ 合并进画布同步协议，减少一套心智负担。
 - 请求体无大小上限，1.8MB+ JSON 任意 POST（app.py:244）→ 设置
   MAX_CONTENT_LENGTH（状态瘦身后 1MB 足够）。


================================================================
三、其他功能的问题与优化
================================================================

----------------------------------------------------------------
安全（远程/公网使用前必须处理）
----------------------------------------------------------------
 1. 任意文件读取（最严重）：/api/file-content 和 /api/file-raw
    （app.py:2168-2234）的 path 参数没有做 realpath + startswith 校验
    （/maps/、/resources/ 有做，这两个没有），可用 ../ 读到项目外文件。
    配合 debug=True（app.py:2961）暴露的 Werkzeug 调试器，等于远程代码
    执行风险。方案：统一封装一个 safe_resolve(base, user_path)，所有
    文件类端点走它；生产启动改 debug=False + waitress/gevent 部署。
 2. 无鉴权、身份自报：DM 判定靠 IP（app.py:2463-2485），角色列表过滤靠
    客户端传 ?role=DM（app.py:479）；任何人可调用 /api/custom/* 增删
    资料、冒名发聊天。方案：加入房间时发一个随机 session token（存内存
    即可），后续请求带 token，服务端据 token 查 role——不需要完整用户
    系统，几十行就能把"自报身份"变成"服务端认定身份"。
 3. XSS：聊天消息不转义（app.py:2497-2500），_strip_ansi 还主动产出
    HTML 标签（app.py:1997-2018）；若前端 innerHTML 渲染即可注入脚本。
    方案：入库前 html.escape，ANSI 转换放在转义之后。
 4. 上传扩展名校验：malware.jpg.exe 类多重扩展名能过白名单
    （app.py:2888）。

----------------------------------------------------------------
轮询风暴：建议合并为一个通道
----------------------------------------------------------------
前端目前同时跑 6 个定时器：画布 300ms、聊天 1.5s、提及 2s、心跳/战斗/
自动保存 3s、HP 5s（map.js:2957,2991,3150,3440,3441,3468,4298）。
既然已经有 WS，聊天、提及、战斗状态、在线名单、HP 变化都可以走同一条 WS
推送（消息加 channel 字段），心跳用 WS 的连接存活代替。这样把每分钟上百个
HTTP 请求压缩成一条长连接，手机端玩家的电量和流量都会好很多。

----------------------------------------------------------------
多人状态隔离
----------------------------------------------------------------
 - active_char_id 是全局变量（app.py:113），多玩家同时操作会互相覆盖当前
   角色——应改为按 session/IP 维度的字典。
 - 画布、战斗、聊天都是全局单例，开第二个团要手动清场；如果有多团需求，
   值得引入最简"房间 id"作为所有状态的外层 key。

----------------------------------------------------------------
代码质量（dnd_bot.py / app.py）
----------------------------------------------------------------
 - _roll_event_table（dnd_bot.py:2248-2370）与 _process_check_chain
   （dnd_bot.py:1976-2098）中同一段「子表解包+跳转」逻辑重复 3 次、嵌套
   5-6 层——链式跳转已有 SUB_TABLE_REGISTRY，可重构为循环+统一的
   resolve_entry()，天然支持任意深度而不是硬编码 4 层。
 - 14 个随机表命令函数体完全一致（dnd_bot.py:2375-2466），可用注册表+
   闭包生成。
 - cmd_log() 约 300 行单函数（dnd_bot.py:2486-2800），建议拆分；且
   _session_log 只在手动 .log 时落盘，进程崩溃全丢——建议每 N 条追加写
   一个 jsonl 兜底。
 - app.py 存在重复路由定义 /api/spells/search（app.py:861 vs 1445），
   后者会覆盖或冲突，需清理。
 - 大量 except Exception: pass 吞错（app.py:131,139,207,284 等），至少
   打日志。


================================================================
四、建议实施顺序
================================================================

第 1 步（半天~1天）：图片出 JSON（P0-1）+ 共享状态加锁（P0-3）+ 删除
  ws_server.py 死代码 + debug=False
  → 收益：同步流量降 95%+，数据不再有损坏风险

第 2 步（1天）：修 4 个前端同步 bug：推送时检查 WS、重连拉全量、拖拽保护
  +差量 DOM、笔迹按 uuid 去重
  → 收益：多人同时操作不再丢状态

第 3 步（2-3天）：操作语义化消息 + 单调版本号（P1-1），顺带支持删除同步
  → 收益：同步协议根本性变可靠

第 4 步（2-3天）：session token 鉴权 + 服务端迷雾过滤（P0-2 依赖此步）+
  文件路径校验 + XSS 转义
  → 收益：可以放心开公网/内网穿透

第 5 步（2-3天）：各轮询合并进 WS 单通道
  → 收益：移动端体验、服务器负载

其中第 1、2 步性价比最高：不改协议、不动数据结构，就能把「拖一下图层广播
几十 MB」和「两人同画互相覆盖」这两个最影响实际跑团体验的问题解决掉。
