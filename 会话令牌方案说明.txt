会话令牌（Session Token）方案说明
—— 骰娘 Web 版公网安全加固设计（未实施，待确认）
整理日期: 2026-07-17

一、会话令牌是什么
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

一句话解释:
    一串由服务器生成的随机字符串，相当于进场时发给每个玩家的
    "一次性手环"——之后玩家每次请求都出示这个手环，服务器靠
    它认人，而不是靠玩家自己"报名字"。

现在的流程（自报家门，无凭证）:
    玩家 → 服务器: 我叫"小华"，我要发聊天消息
    服务器: 好的，我信了。（没有任何验证）

    问题: 任何拿到樱花隧道地址的人，都可以声称自己是"小华"、
    声称自己是 DM、甚至直接调 API 删角色清画布。

加了会话令牌之后:
    ① 进房间:
       玩家 → 服务器: 我叫"小华"，房间口令是 XXXX
       服务器: 验证口令 → 生成随机令牌 "a3f8...c2" 发给他
               并在内存里记下: a3f8...c2 = 小华(PL)
    ② 之后每次请求:
       玩家 → 服务器: [令牌: a3f8...c2] 我要移动 token
       服务器: 查表 → 这是小华，PL 身份 → 允许
    ③ 陌生人:
       → 服务器: 我要清空画布
       服务器: 没有令牌/令牌无效 → 拒绝 (401)

能解决的具体问题:
    ┌────────────────────────────┬──────────────────┬────────────────────────┐
    │ 问题                       │ 现状             │ 有令牌后               │
    ├────────────────────────────┼──────────────────┼────────────────────────┤
    │ 陌生人拿到樱花地址乱搞     │ 随便调任何 API   │ 没进过房间就没令牌，   │
    │                            │                  │ 一律拒绝               │
    │ frp 下所有人同 IP 重名顶号 │ 输别人名字能顶号 │ 名字绑定令牌，顶号无效 │
    │ DM 身份靠 IP 判断          │ frp 下不可靠     │ 令牌记录角色，         │
    │                            │                  │ 服务器端认定           │
    │ 迷雾数据发给玩家(P0-2)     │ 无法区分谁是 DM  │ 能区分 → 才能做        │
    │                            │                  │ 服务端过滤             │
    └────────────────────────────┴──────────────────┴────────────────────────┘

它"不是"什么:
    - 不是注册账号系统——不需要注册、密码，不存数据库。
      令牌存在服务器内存里，重启即清空，下次跑团重新进房即可。
    - 不是加密——只解决"你是谁"(身份认证)，不加密传输内容。
      对跑团场景足够。
    - 对玩家完全无感: 进房时输一次名字(可选加 DM 设的房间口令)，
      浏览器自动保存令牌并在每次请求携带，之后无需任何操作。

实现成本:
    约几十行代码: 进房接口发令牌 → 前端 fetch/WS 统一带上 →
    服务器加一个校验函数套在需要保护的接口上。
    不改变任何现有玩法和界面。

二、发放/验证流程与存储位置
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

核心认知: 玩家永远不需要"输入令牌"
    令牌是浏览器和服务器之间自动传递的，玩家全程看不到它。
    玩家最多只在第一次进房时输入一个"房间口令"(DM 设置的，
    比如 woshidm123)——口令是给人记的，令牌是给机器用的，
    这是两个东西。

判断"第几次进房"的完整流程:
    进房请求永远带两样东西: 名字 + 本浏览器存过的令牌(可能没有)

    玩家点击"进入房间" (浏览器自动附带 localStorage 里的令牌)
            │
            ▼
    ┌─ 服务器检查 ──────────────────────────────────────┐
    │ ① 带了令牌，且令牌在登记表中、名字对得上           │
    │    → 老玩家回来了(刷新页面/断线重连)               │
    │    → 直接放行，无感恢复身份，不发新令牌             │
    │                                                  │
    │ ② 没带令牌(或已失效)，且该名字当前无人使用          │
    │    → 第一次进房(或服务器重启后重新进房)             │
    │    → 验证房间口令 → 通过则生成新令牌发给他          │
    │                                                  │
    │ ③ 没带令牌，但该名字已被持有效令牌的人占用          │
    │    → 有人想顶号(或玩家换了设备)                    │
    │    → 拒绝: "该ID已在线"                           │
    └──────────────────────────────────────────────────┘

    所以不存在"第二次进房要求玩家输入令牌"这回事——
    第二次进房时浏览器自动出示上次存的令牌，走 ① 直接通过。
    玩家的体验是: 第一次输名字+口令，以后打开网页直接进。

令牌存在哪里:
    ┌──────────┬──────────────────────────┬────────────────────────────┐
    │ 端       │ 存储位置                 │ 特性                       │
    ├──────────┼──────────────────────────┼────────────────────────────┤
    │ 玩家浏览 │ localStorage             │ 关浏览器/重启电脑都还在;   │
    │ 器       │ (网页本地存储)           │ 换设备/换浏览器就没有了;   │
    │          │                          │ 清浏览器数据也会丢         │
    ├──────────┼──────────────────────────┼────────────────────────────┤
    │ 服务器   │ 内存字典                 │ 纯内存版: 重启全部失效;    │
    │          │ {令牌:{名字,身份,时间}}  │ 带json持久化版: 重启后     │
    │          │ 可选同时写入小 json 文件 │ 老玩家仍能无感重连         │
    └──────────┴──────────────────────────┴────────────────────────────┘

三个边界情况:
    1. 服务器重启(纯内存版): 所有令牌失效 → 浏览器旧令牌对不上
       → 但登记表已空、名字全部空闲 → 走流程②用口令重新领令牌。
       玩家感受只是"重新点了一次进入房间"。
    2. 玩家换手机/换电脑: 新设备无 localStorage → 名字被旧会话
       占着 → 走③被拒。解法(可都做):
       - 旧设备 10 秒无心跳自动清离线 → 等 10 秒再进;
       - 给 DM 一个"踢人"按钮，手动释放名字。
    3. 玩家清了浏览器缓存: 同"换设备"，等旧会话超时后重进。

三、对骰娘的实际形态（樱花 frp 场景）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

    - DM 启动服务器时(或在页面上)设置一个房间口令，
      跑团前发到玩家群里;
    - 玩家第一次打开页面: 输入 名字+口令 → 进入，
      浏览器自动存令牌;
    - 之后整场跑团(刷新、断线、隔天再开)都不需要再输任何东西;
    - 陌生人拿到樱花隧道地址: 没口令进不了房，没令牌调不了 API。

配套建议(与之前优化方案的"第4步"一起实施):
    1. 会话令牌鉴权(本文档方案)
    2. /api/file-content 等接口的文件路径校验(堵路径穿越)
    3. P0-2 服务端迷雾过滤(依赖令牌区分 DM/玩家)
    三者共用同一套身份体系。

樱花 frp 使用注意(实施前的临时措施):
    - 隧道地址只私下发给跑团成员，不要公开;
    - 不跑团时关闭 frpc，不要 24 小时挂着。

四、DM/PL 身份变更的识别机制
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

核心设计原则: 令牌只管"你是谁"，不管"你能干什么"
    身份(role)不写在令牌里，而是写在服务器的登记表里:

        服务器登记表(内存):
            令牌 a3f8...c2  →  { 名字: 老王, 身份: DM }
            令牌 b7e1...9d  →  { 名字: 小华, 身份: PL }

    每次请求进来，服务器拿令牌实时查表得到当前身份。
    所以变更身份 = 改登记表里的一个字段，令牌本身不用换，
    玩家也无感——下一次请求起权限就自动变了。
    (若身份写死在令牌里，换身份就得重新发牌，这是把身份
    放服务器端的好处。)

场景①: 跑团中途转让 DM（最常见: 老王有事，小华接任）
    老王(现任DM) 点击"转让DM给小华"
        → 服务器验证: 发起者令牌查表 = DM ✅ 有权转让
        → 登记表修改: 老王 → PL, 小华 → DM
        → 立即生效: 小华下一次请求就是DM权限,
                    老王的DM按钮下一次心跳后消失
    只有现任 DM 的令牌能发起转让——PL 调用此接口直接拒绝,
    所以玩家无法自封 DM。

场景②: DM 掉线/失联，需要有人顶上
    现任 DM 不在，没人能"转让"。采用两级口令设计:
        - 房间口令: 进房用的，所有人都知道;
        - DM 口令: 只有该当 DM 的人知道的另一个口令
          (服务器启动时设置)。
    DM 位空缺(原 DM 离线超时)时，任何在房玩家输入 DM 口令
    即可认领 DM。原 DM 回来后自动降为 PL(或由新 DM 转回)。

场景③: 进房时选错身份
    - PL 想变 DM: 走场景②的 DM 口令认领(DM位空时)，
      或请现任 DM 转让;
    - DM 想变 PL: 自己点"卸任"即可(登记表改字段)。
    均不需要退出重进——身份在登记表里，改表即可。

场景④: 变更后各端界面怎么跟着变
    身份变更的权威在服务器，前端通过两条已有通道自动感知:
    1. 心跳响应(每3秒)里带上"你当前的身份"
       → 前端据此切换界面(📤推送按钮显隐、迷雾渲染模式等);
    2. 数据内容本身: 做了 P0-2 服务端迷雾过滤后，服务器按
       "请求令牌的当前身份"决定发不发迷雾下的内容——
       小华变成 DM 的那一刻起，他拉到的画布数据里自动就包含
       迷雾下的 token，反之老王降为 PL 后自动看不到。

场景⑤: 断线重连 / 换天继续跑
    令牌不变 → 查表 → 身份还是变更后的状态。
    转让过的 DM 身份在重连后依然保持，不会跳回。

与现状对比:
    ┌────────────┬──────────────────────┬──────────────────────┐
    │            │ 现状                 │ 令牌方案             │
    ├────────────┼──────────────────────┼──────────────────────┤
    │ 身份依据   │ 客户端自报 ?role=DM  │ 服务器登记表，       │
    │            │ + IP 猜测            │ 每次请求实时查       │

    │            │ 器/重新抢)           │ 即时生效             │
    │ 防冒充     │ 无                   │ PL令牌调DM接口       │
    │            │                      │ 直接 401             │
    └────────────┴──────────────────────┴──────────────────────┘

五、登记表的查看与编辑权限
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

登记表在哪:
    存在服务器进程的内存里(web/app.py 运行时的一个字典)。
    如果做持久化，会同步写到文件 web/session_tokens.json:

        {
          "a3f8...c2": { "name": "老王", "role": "DM", "joined_at": "..." },
          "b7e1...9d": { "name": "小华", "role": "PL", "joined_at": "..." }
        }

四级权限:
    ┌──────────────┬────────────────────┬──────────────────┬────────────────────┐
    │ 谁           │ 能看什么           │ 能改什么         │ 在哪操作           │
    ├──────────────┼────────────────────┼──────────────────┼────────────────────┤
    │ 跑服务器的人 │ 全部，包括令牌值   │ 任意: 改文件、   │ 服务器电脑上用     │
    │ (物理管理员, │ (直接打开json文件) │ 重启清空         │ 记事本打开json,    │
    │ 通常即DM本人)│                    │                  │ 或重启 --web       │
    ├──────────────┼────────────────────┼──────────────────┼────────────────────┤
    │ DM           │ 在线名单: 名字/    │ 仅两个受限动作:  │ 网页聊天侧栏       │
    │ (凭DM令牌)   │ 身份/在线状态/     │ 踢人(删条目)、   │ "在线用户"面板,    │
    │              │ 进房时间。         │ 转让DM(改role)   │ DM视角多出踢人/    │
    │              │ 看不到任何人令牌值 │                  │ 转让按钮           │
    ├──────────────┼────────────────────┼──────────────────┼────────────────────┤
    │ PL           │ 在线名单(名字+     │ 无任何编辑权     │ 网页在线用户面板   │
    │              │ 身份)，同现在      │                  │ (只读)             │
    ├──────────────┼────────────────────┼──────────────────┼────────────────────┤
    │ 陌生人       │ 什么都看不到       │ 无               │ 无入口             │
    │ (无令牌)     │                    │                  │                    │
    └──────────────┴────────────────────┴──────────────────┴────────────────────┘

三个关键设计点:
    1. 令牌值永远不在网页上显示给任何人(包括DM)。
       网页接口返回的登记表视图只有"名字/身份/在线状态"，
       令牌列被服务器裁掉。每个玩家的浏览器只知道自己那一个
       令牌。即使 DM 的屏幕被直播/截图，也不会泄露任何人的
       通行凭证。
    2. "编辑"不是直接改表格，而是通过受保护的动作接口。
       DM 只有"踢出这个人""转让DM给这个人"两个按钮——
       每个按钮背后的接口都先验证发起者的令牌确实是 DM。
       把能改的范围收窄到最小，不给误操作和越权留空间。
    3. 物理管理员是最终兜底。任何情况搞乱了(DM口令忘了、
       登记表状态异常)，跑服务器的人重启一次
       python dnd_bot.py --web 就回到干净状态，
       所有人重新进房领新令牌。服务器跑在 DM 自己电脑上
       (经樱花frp暴露)，这个终极权限天然在自己手里。

注意事项:
    若启用 json 持久化版: session_tokens.json 里含有效令牌值，
    这个文件不要发给别人、不要截图——拿到它等于拿到所有人的
    手环。(纯内存版没有这个问题，代价是服务器重启后大家要
    重新进房。)
