┌─────────────────────────────────────────────────────────────────────────────────┐
│ 1.2 事件表数据源统一                                                              │
├─────────────────────────────────────────────────────────────────────────────────┤
│ 优先级: ⭐⭐⭐⭐⭐  复杂度: 🔴 高                                                 │
├─────────────────────────────────────────────────────────────────────────────────┤
│ 现状:                                                                           │
│   同一套事件表在三处独立维护：                                                     │
│   ① north-expedition.html — JavaScript TABLES 对象（前端渲染用）                  │
│   ② dnd_bot.py — Python 字典（CLI 机器人用）                                     │
│   ③ data/随机事件表.txt — 文字版参考文档                                          │
│                                                                                 │
│ 问题:                                                                           │
│   • 三处需手动同步，极易出现不一致                                                 │
│   • 已在多处发现 CLI 和 Web 端事件表不同步的历史问题                               │
│   • 新增/修改事件需要改3个地方，工作量大且易出错                                   │
│   • 缺少版本比对工具，不知道哪里不一致                                             │
│                                                                                 │
│ 建议:                                                                           │
│   建立单一数据源（Single Source of Truth）:                                       │
│                                                                                 │
│   方案A（推荐）: JSON 主数据源 + 自动生成                                          │
│     • 创建 data/event_tables.json 作为唯一的事件表定义文件                        │
│     • 编写脚本 generate_event_code.py：                                          │
│       → 生成 JS 的 TABLES 对象（注入到 north-expedition.html）                    │
│       → 生成 Python 的事件字典（供 dnd_bot.py import）                            │
│       → 生成 TXT 参考文档                                                        │
│     • 构建时自动运行，或在事件表变更后手动运行一次                                  │
│                                                                                 │
│   方案B: Python 主数据源 + 前端 API                                               │
│     • 事件表定义仅在 dnd_bot.py 维护                                              │
│     • 前端通过 /api/event-tables 接口获取事件表数据                               │
│     • 前端缓存到 localStorage，启动时刷新                                         │
│     • CLI 端直接引用 Python 字典                                                  │
│     • TXT 文档通过脚本自动生成                                                    │
│                                                                                 │
│ 风险: 方案A需要迁移现有数据 + 确保生成代码的正确性                                  │
│ 收益: 一修改全同步、消除不一致bug、大幅降低维护成本                                │
└─────────────────────────────────────────────────────────────────────────────────┘

│ 现状:                                                                           │
│   • 身份系统仅基于用户自选ID+颜色，无真实认证                                       │
│   • sessionStorage 存储身份信息，完全依赖客户端                                    │

│   分级实施：                                                                     │
│                                                                                 │
│   阶段1（最小成本）:                                                              │
│     • 引入简单的房间密码机制（DM创建时设置，加入时验证）                            │

│                                                                                 │
│   阶段2（中期）:                                                                  │
│     • 接入 OAuth2.0（GitHub / Google / Discord 登录）                             │
│     • 用户系统数据库表（用户名、邮箱、角色绑定、统计数据）                          │
│     • JWT token 认证                                                             │
│                                                                                 │
│   阶段3（远期）:                                                                  │
│     • 完整的权限管理系统（RBAC）                                                   │
│     • 房间级别的访问控制                                                           │
│     • 操作审计日志                                                                │
│                                                                                 │
│ 风险: 阶段2需要接入第三方服务，需评估合规性                                         │

┌─────────────────────────────────────────────────────────────────────────────────┐
│ 2.2 输入验证与安全加固                                                            │
├─────────────────────────────────────────────────────────────────────────────────┤
│ 优先级: ⭐⭐⭐⭐   复杂度: 🟢 低                                                  │
├─────────────────────────────────────────────────────────────────────────────────┤
│ 现状:                                                                           │
│   • 多处 API 直接使用用户输入，无系统性验证                                         │
│   • 无 CSRF 保护（Flask 默认无）                                                  │
│   • 头像上传虽有扩展名检查，但缺乏内容类型验证                                      │
│   • 骰子表达式解析可能有注入风险（如 ! 爆炸骰滥用）                                 │
│   • WebSocket 消息无格式校验                                                     │
│                                                                                 │
│ 建议:                                                                           │
│   ① 添加 Flask-WTF 或手动 CSRF token 保护                                       │
│   ② 所有 API 输入添加类型/长度/范围校验                                           │
│   ③ 头像上传增加 MIME 类型检测（不仅检查扩展名） + 文件大小限制                    │
│   ④ 骰子表达式增加复杂度限制（防爆炸骰无限递归）                                   │
│   ⑤ WebSocket 消息增加 JSON Schema 校验                                          │
│   ⑥ 添加请求频率限制（Flask-Limiter）— 防滥用                                     │
│   ⑦ 文件路径操作改用 pathlib + 规范化（防路径遍历）                                │
│                                                                                 │
│ 风险: 低，都是局部修改                                                            │
│ 收益: 安全性显著提升、防止恶意输入导致崩溃或数据泄露                                │
└─────────────────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────────────────┐
│ 3.1 大型 JSON 数据文件加载优化                                                     │
├─────────────────────────────────────────────────────────────────────────────────┤
│ 优先级: ⭐⭐⭐⭐   复杂度: 🟡 中                                                  │
├─────────────────────────────────────────────────────────────────────────────────┤
│ 现状:                                                                           │
│   • spells_full.json — 504KB（936条法术，每次启动加载到内存）                      │
│   • monsters_full.json — 192KB（557条怪物）                                       │
│   • chm_search_index.json + chm_inverted_index.json                              │
│   • CHM 提取数据 139MB（五版不全书 HTML 详情页）                                   │
│   • 每次搜索法术/怪物时全量遍历 JSON 数组                                          │
│                                                                                 │
│ 问题:                                                                           │
│   • spells_full.json 全量加载到内存，但实际访问频率不均                            │
│   • CHM 搜索虽有倒排索引，但加载索引也需要时间                                     │
│   • 没有分页机制，一次返回所有结果                                                 │
│                                                                                 │
│ 建议:                                                                           │
│   ① 法术/怪物数据改用 SQLite 存储（已有 characters.db 的 SQLite 基础设施）         │
│      → 按需查询，支持模糊搜索、分页、索引                                          │
│      → 减少内存占用                                                              │
│   ② 或至少添加内存缓存（functools.lru_cache）                                     │
│   ③ API 搜索结果添加分页（limit + offset）                                        │
│   ④ CHM 索引改为按需加载（首次搜索时才加载，延迟初始化）                            │
│                                                                                 │
│ 风险: 中 — 需要迁移数据和修改查询逻辑                                              │
│ 收益: 启动速度加快、内存占用降低、搜索结果可控、API 响应更快                        │
└─────────────────────────────────────────────────────────────────────────────────┘


┌─────────────────────────────────────────────────────────────────────────────────┐

│   ④ 添加 /api/stats 端点（在线人数/内存使用/运行时长）                              │

│                                                                                 │
│  ⑧ combat.py 仅 166 行但 tracker 是全局变量                                        │
│     → 不支持多房间/多战斗并行                                                      │
│                                                                                 │
│  ⑨ localStorage 直接写入（无配额检查 + 无编码处理）                                │
│     → 超限时静默失败，用户数据可能部分丢失                                         │
